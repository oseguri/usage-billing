# 결정 기록

결정마다 고른 것, 이유, 버린 대안을 적는다.

## 원장 스키마 (V1, 2026-11-17)

### 계정 식별자는 BIGINT 자동 증가
- 이유: 원장의 모든 줄에 계정 번호가 들어간다. 줄이 수천만 건이 되면 키 크기가 그대로 표와 인덱스 크기가 된다. InnoDB는 기본 키 순서로 저장하므로 순서대로 늘어나는 값이 삽입에 유리하다.
- 버린 대안: UUID 문자열. 밖에 노출해도 추측할 수 없다는 장점이 있지만, 계정 번호는 내부에서만 쓴다.

### 시스템 계정의 소유자는 'SYSTEM'
- 이유: 유일 제약 (owner_id, account_type)이 시스템 계정에도 걸려야 한다. MySQL은 NULL끼리 서로 다른 값으로 보기 때문에, 소유자를 NULL로 두면 외부 계정이 두 개 생길 수 있다.
- 버린 대안: NULL.

### 계정 종류와 거래 종류는 ENUM
- 이유: 돈의 흐름을 정하는 값이라 정해진 값만 들어가야 한다. 목록 끝에 값을 추가하는 것은 표를 다시 쓰지 않는다.
- 버린 대안: 문자열. 오타가 들어갈 수 있다.

### 금액은 BIGINT, 단위는 micros (1원 = 1,000,000)
- 이유: 소수형은 더할 때 오차가 쌓인다. 호출 한 건의 비용이 1원보다 작을 수 있어서 원 단위로는 반올림 오차가 생긴다. BIGINT로 약 9조 원까지 담는다.
- 금액 칸 이름은 전부 `_micros`로 끝낸다.
- 버린 대안: DECIMAL. 정확하지만 코드에서 BigDecimal을 써야 한다.

### 잔액은 account와 다른 표(account_balance)에 둔다
- 이유: account는 거의 읽기만 하고 잔액은 계속 바뀐다. 원장에 줄을 넣을 때 외래 키 검사가 account의 줄에 읽기 락을 거는데, 잔액이 같은 줄에 있으면 잔액 수정과 부딪힌다.

### 음수 잔액은 DB와 코드 양쪽에서 막는다
- DB: `CHECK (allow_negative OR balance_micros >= 0)`. 외부 계정만 allow_negative가 참이다.
- 이유: 코드에 버그가 있어도 DB가 마지막에 막는다. CHECK는 같은 줄의 칸만 볼 수 있어서 계정 종류를 직접 볼 수 없다. 그래서 allow_negative 칸을 따로 뒀다.
- 치른 것: 계정 종류에서 정해지는 값을 두 표에 나눠 갖는다. 계정을 만드는 코드 한 곳에서만 이 값을 정한다.
- 영향: 기준선 실험(E0)은 음수 잔액 건수가 아니라 CHECK에 걸린 횟수를 센다.

### 멱등 키의 유일 제약은 (tx_type, idempotency_key)
- 이유: 멱등 키는 원인이 된 것의 번호를 쓴다(결제 번호, 시도 번호). 같은 시도에 예약 거래와 정산 거래가 따로 생기므로 키만으로는 겹친다.
- 멱등 키는 같은 사건이면 다시 보내도 같은 값이어야 한다. 요청을 받을 때 새로 만드는 값은 쓸 수 없다.
- 버린 대안: 키 앞에 종류를 붙이는 방식(`settle:77`). 코드가 규칙을 지켜야 한다.

### 원장 줄의 금액은 부호로 방향을 나타낸다
- 빠지면 음수, 들어오면 양수. 0은 CHECK로 막는다.
- 이유: 계정 잔액, 거래별 합, 장부 전체 합이 전부 `SUM(amount_micros)`로 끝난다.
- 버린 대안: 방향 칸과 양수 금액. 회계에서 익숙한 방식이지만 합계마다 CASE가 필요하다.

### 원장 줄에 생성 시각을 두지 않는다
- 이유: 거래(ledger_tx)에 이미 있다. 줄이 가장 많은 표라 한 줄을 작게 둔다.
- 치른 것: 내역에 시각을 보여 주려면 ledger_tx와 조인한다.

### 원장 줄에 외래 키를 건다
- 이유: 없는 거래나 계정을 가리키는 줄이 생기지 않는다.
- 치른 것: 줄을 넣을 때마다 대상 표를 확인한다. 처리량에 주는 영향은 E1에서 잰다.

### 한 거래의 합이 0이라는 규칙은 DB 제약으로 걸지 않는다
- 이유: CHECK는 한 줄만 본다. 여러 줄의 합은 볼 수 없다.
- 대신: 거래를 기록하는 코드가 넣기 전에 검사하고, 검사기가 실행 뒤에 다시 확인한다.

### 지금 넣지 않은 것
- account_balance의 버전 칸: 낙관적 락을 실험할 때 새 버전 파일로 추가한다.
- ledger_tx의 원인 칸: 멱등 키가 원인의 번호라 지금은 필요 없다. 대조 배치에서 조회가 불편하면 추가한다.

## 시스템 계정 (V2, 2026-11-20)

### 시스템 계정 3개는 Flyway로 미리 넣는다
- EXTERNAL(바깥에서 들어온 돈), USAGE(정상 과금), PLATFORM_LOSS(플랫폼이 떠안은 손실). 전체에 하나씩이고 소유자는 'SYSTEM'이다.
- 이유: 모든 거래의 합이 0이어야 하므로 충전과 정산에 상대편 계정이 필요하다. 첫 거래 전에 있어야 해서 표를 만드는 것과 같은 방식으로 넣는다.
- 계정마다 account와 account_balance에 한 줄씩 넣는다. 잔액 줄이 없으면 잔액 UPDATE가 0줄에 적용되고 오류 없이 지나간다.

### 잔액 줄의 계정 번호는 적지 않고 account에서 조회해 넣는다
- `INSERT ... SELECT ... WHERE owner_id = 'SYSTEM'`. allow_negative는 `account_type = 'EXTERNAL'`로 채운다.
- 이유: 자동 증가는 겹치지 않는 번호만 약속하고 1부터 연속이라는 것은 약속하지 않는다. 취소된 INSERT도 번호를 쓴다. 로컬 DB에서 시험 삽입을 한 번 ROLLBACK했으므로, 이 DB에 V2를 적용하면 1, 2, 3이 아닌 번호가 나올 것이다(적용 뒤 확인).
- 영향: 코드도 시스템 계정을 번호 상수가 아니라 (owner_id, account_type)으로 찾는다.
- 버린 대안: id를 1, 2, 3으로 직접 지정. 코드에서 상수로 쓸 수 있지만 같은 약속이 SQL과 코드 두 곳에 생긴다.

### 미정: 손실 분개의 상대 계정
- 공급자는 청구했는데 응답을 못 받은 경우, 플랫폼이 부담하기로 했다(사용자에게 과금하지 않음).
- 계획서의 분개(RESERVED → PLATFORM_LOSS)는 예약금이 사용자 돈이라서 실제로는 사용자가 낸다. 결정과 어긋난다.
- 플랫폼이 부담하려면 예약을 지갑으로 전액 돌려주고, PLATFORM_LOSS에 더하는 금액의 상대편이 따로 있어야 한다. 후보: EXTERNAL, 플랫폼 자금 계정 신설.
- 본 3주차 대조 배치에서 정한다.

## 거래 기록 기능 (2026-11-20)

### Service와 Repository 두 층으로 나눈다
- LedgerService: 입력 검사, SQL을 부르는 순서, 트랜잭션 경계(`@Transactional`).
- LedgerRepository: SQL 실행만 한다. 필요한 값은 전부 인자로 받는다.
- 입력은 거래 종류(TxType), 멱등 키, 줄 목록(LedgerLine: accountId, amountMicros). 돌려주는 것은 생성된 거래 번호.
- Controller는 두지 않는다. 이 기능은 HTTP로 불리지 않고 충전·예약·정산이 내부에서 부른다.

### 원장 경로는 JPA가 아니라 JdbcTemplate
- 이유 1: JPA의 기본 수정은 읽고, 계산하고, 저장하는 방식이라 동시 요청에서 갱신이 사라진다. 잔액 100에 A가 +50, B가 +30을 동시에 하면 둘 다 100을 읽고 150과 130을 차례로 저장해서 180이 아니라 130이 된다.
- 이유 2: 어떤 SQL이 언제, 어떤 순서로 나가는지 직접 정해야 한다. 잠금 순서와 E1의 락 방식 비교에 필요하다. JPA는 수정을 모았다가 트랜잭션 끝에 보낸다.
- 이유 3: 원장은 넣기만 하는 표라서 변경을 추적해 주는 JPA의 장점을 쓸 일이 없다.
- 이유 4: UPDATE가 바꾼 줄 수를 결과로 써야 한다.
- 버린 대안: JPA에 `@Version`이나 `FOR UPDATE`를 붙이는 방식. 가능하지만 이 경로에서는 SQL을 직접 쓰는 편이 통제하기 쉽다. 차이는 E1에서 잰다.

### 잔액은 SQL 한 문장으로 더한다
- `UPDATE account_balance SET balance_micros = balance_micros + ? WHERE account_id = ?`
- 이유: DB가 그 줄을 잠근 채 더하므로 위의 갱신 유실이 생기지 않는다.
- 줄마다 한 문장씩 실행한다. 거래 하나의 줄이 2~3개이고, 줄마다 바뀐 줄 수를 확인하기 쉽다. 묶어 보내는 방식(`rewriteBatchedStatements`)의 효과는 E1에서 잰다.

### 잘못된 입력은 DB에 닿기 전에 코드에서 막는다
- 줄이 2개 미만, 금액이 0인 줄, 합이 0이 아닌 경우. `IllegalArgumentException`을 던진다.
- 합은 `Math.addExact`로 구한다. long 범위를 넘으면 틀린 값이 되는 대신 예외가 난다.
- 금액 0은 DB의 CHECK도 막지만, 코드에서 먼저 막으면 거래를 넣었다가 취소하는 일이 없다.

### 잔액 줄이 없는 계정이면 전체를 취소한다
- 잔액 UPDATE가 바꾼 줄 수가 1이 아니면 `IllegalStateException`을 던진다.
- 이유: 그냥 지나가면 원장에는 줄이 있는데 잔액에는 반영되지 않는다. 입력이 아니라 데이터가 깨진 것이라 IllegalArgument가 아니라 IllegalState다.

### CHECK에 걸리면 이미 넣은 거래와 줄도 함께 취소된다
- 통합 테스트로 확인했다. 음수가 허용되지 않는 계정을 음수로 만드는 거래를 넣으면 `UncategorizedSQLException`(MySQL 오류 3819, `chk_account_balance_non_negative`)이 나고, ledger_tx에 그 멱등 키가 0건이며 두 계정의 잔액이 그대로다.
- 취소하는 것은 `@Transactional`이다. RuntimeException이 메서드 밖으로 나가야 롤백된다.

### 테스트는 실행 순서에 기대지 않는다
- 통합 테스트는 같은 DB를 이어서 쓰고, JUnit은 테스트 순서를 약속하지 않는다.
- 잔액은 절댓값이 아니라 기록 전과의 차이로 확인한다. 음수를 만드는 금액은 기록 전 잔액 + 1로 계산한다. 멱등 키는 테스트마다 새로 만든다.
- 예외는 넓게 잡지 않는다. 클래스를 좁히고 메시지까지 확인한다. RuntimeException으로 잡았을 때, 합이 0이 아니어서 검사에서 거부된 것을 CHECK 위반으로 착각한 적이 있다.
- 테스트에 `@Transactional`을 붙이지 않는다. 서비스의 트랜잭션이 테스트의 것에 합쳐져서 서비스가 스스로 롤백하는지 확인할 수 없다.
- 테스트 DB는 개발 환경과 같은 mysql:8.4로 고정한다.

### 잔액 부족은 InsufficientBalanceException으로 바꿔 던진다 (2026-11-23)
- 바꾸는 곳은 Repository다. MySQL 오류 번호(3819)와 제약 이름은 DB에 속한 지식이라 Service가 알지 않게 한다.
- 오류 번호가 3819이고 메시지에 `chk_account_balance_non_negative`가 있을 때만 바꾼다. 다른 CHECK 위반이나 다른 오류는 그대로 다시 던진다.
- 예외에 계정 번호를 담고, 원래 예외를 원인(cause)으로 넘긴다.
- RuntimeException을 상속하므로 `@Transactional`이 롤백한다.

### 같은 멱등 키가 다시 오면 첫 거래의 번호를 돌려준다 (2026-11-24)
- 같은 (tx_type, idempotency_key)로 `record`가 다시 불리면 예외를 던지지 않고 첫 거래의 번호를 반환한다. 줄 삽입과 잔액 반영은 건너뛴다.
- 이유: 보내는 쪽은 응답을 못 받으면 같은 요청을 다시 보낸다. 이미 처리한 요청에 실패로 답하면 계속 다시 보낸다.
- 버린 대안: 예외를 던진다. 돈은 유일 제약이 지켜 주지만, 처리가 끝난 요청이 실패로 보인다.

### 먼저 조회하지 않고 먼저 넣는다
- `ledger_tx`에 INSERT를 시도하고, `DuplicateKeyException`이 나면 (tx_type, idempotency_key)로 기존 번호를 조회한다.
- 이유: 조회 결과는 읽은 순간의 사실이라 INSERT할 때는 낡았을 수 있다. 두 요청이 모두 "없음"을 읽고 둘 다 넣으려 할 수 있다. 유일 제약은 확인과 삽입을 DB가 한 동작으로 처리하므로 틈이 없다.
- 먼저 조회하더라도 동시 요청에서는 중복 오류를 잡는 코드가 어차피 필요하다.
- 버린 대안: 조회하고 없으면 넣는다.

### 중복 오류는 Service에서 잡고, 첫 INSERT만 감싼다
- 잡는 곳은 `LedgerService.record`다. 잡은 뒤 할 일(나머지 단계를 건너뛰고 반환)이 순서를 정하는 일이기 때문이다.
- `try`는 `insertLedgerTx` 한 문장만 감싼다. 잡고 정상 반환해도 안전한 이유는 그 트랜잭션이 바꾼 것이 없기 때문인데, 이는 첫 쓰기에서 실패했을 때만 성립한다. 뒤의 문장까지 감싸면, 거기서 난 중복 오류를 삼키고 줄과 잔액이 없는 거래를 커밋할 수 있다.
- MySQL은 실패한 문장만 취소하고 트랜잭션은 살려 두므로, 같은 트랜잭션에서 조회할 수 있다.
- Repository에 `@Transactional`이 없어서, 거기서 올라온 예외를 Service 안에서 잡아도 롤백 표시가 붙지 않는다.
- 제약 이름은 확인하지 않는다. `ledger_tx`의 유일 제약이 `uk_ledger_tx_type_key` 하나이고 `try`가 그 INSERT만 감싸므로, 여기서 나는 `DuplicateKeyException`은 멱등 키 중복뿐이다. `ledger_tx`에 유일 제약이 더 생기면 다시 본다.
- 통합 테스트로 확인했다. 같은 키로 두 번 기록하면 두 번째 반환값이 첫 번째와 같고, 그 키의 ledger_tx가 1건이며, 잔액은 한 번만 변한다.

### 알려진 한계: 같은 키에 다른 내용이 와도 알아채지 못한다
- 지금은 내용을 비교하지 않는다. 같은 키로 금액이나 계정이 다른 요청이 오면 첫 거래의 번호를 돌려준다.
- 위험한 경우: 예약·정산의 키는 우리 코드가 만든다. 키를 만드는 규칙에 실수가 있어 서로 다른 거래가 같은 키를 가지면, 두 번째 거래가 기록되지 않은 채 성공으로 돌아온다.
- 지금 넣지 않는 이유: 비교하려면 기존 줄을 읽어 와 맞춰 봐야 하고, 이 비교가 필요한 호출자가 아직 없다.
- 다시 볼 시점: 충전 API를 만들 때, 예약·정산의 키 규칙을 정할 때.

### 잔액은 account_id 오름차순으로 고친다 (2026-11-24)
- 한 거래가 여러 계정의 잔액을 고칠 때, 줄을 account_id 오름차순으로 정렬해 그 순서로 UPDATE한다. 정렬은 `LedgerService.record`에서 한다. 어떤 SQL을 어떤 순서로 부를지는 Service가 맡기 때문이다.
- 이유: UPDATE가 잡은 잠금은 트랜잭션이 끝날 때까지 풀리지 않는다. 두 거래가 같은 계정 둘을 반대 순서로 고치면 서로 상대가 쥔 잠금을 기다리는 교착이 된다. 모든 거래가 같은 순서로 잠그면, 기다리는 쪽은 아무 잠금도 쥐지 않은 채 기다리므로 고리가 생기지 않는다.
- `ledger_entry`에는 호출한 쪽이 준 순서 그대로 넣는다. INSERT는 새 줄을 만들 뿐이라 다른 거래와 같은 줄을 두고 다투지 않는다.
- 입력 목록은 고치지 않고 정렬된 새 목록을 만든다. 호출한 쪽의 목록을 바꾸지 않기 위해서이고, `List.of`로 만든 목록은 고칠 수도 없다.
- 순서를 맞춰도 대기는 남는다. 같은 계정을 고치는 거래는 앞 거래가 끝날 때까지 기다린다. 대기가 얼마나 되는지는 E1에서 잰다.

### 교착을 직접 만들어 확인했다
- 손으로: mysql 터미널 두 개에서 두 계정을 반대 순서로 UPDATE했다. 뒤에 들어온 쪽이 `ERROR 1213 (40001): Deadlock found when trying to get lock`을 받았고, 기다리던 쪽의 UPDATE는 그 순간 성공했다.
- 교착 오류를 받은 트랜잭션은 MySQL이 전체를 취소한다. 희생자가 직접 ROLLBACK하기 전에 상대의 대기가 풀린 것으로 확인했다. CHECK 위반(3819)과 중복 키(1062)가 실패한 문장만 취소하는 것과 다르다.
- 테스트로: 두 스레드가 반대 순서의 줄로 `record`를 동시에 부르는 것을 50번 반복했다(거래 100건). 정렬 전에는 50건이 `CannotAcquireLockException`(MySQL 오류 1213)으로 실패했다. 정렬 후에는 실패가 0건이고 두 계정의 잔액이 100건만큼 변했다.
- 이 테스트는 확률에 기댄다. 실패하면 교착이 있다는 증거지만, 통과가 없다는 증명은 아니다. 그래서 정렬 전에 실패하는 것을 먼저 확인했다.
- 다른 스레드에서 난 예외는 테스트를 자동으로 실패시키지 않는다. 모아서 마지막에 확인한다.

### 한 거래에 같은 계정은 한 줄만 허용한다 (2026-11-24)
- 같은 account_id가 두 줄에 나오면 `IllegalArgumentException`을 던진다. 호출하는 쪽이 계정별로 금액을 합쳐서 넘긴다.
- 이유: 잔액 CHECK는 UPDATE 한 문장마다 검사된다. 같은 계정에 빼는 줄과 더하는 줄이 함께 있으면, 최종 잔액은 음수가 아닌데도 빼는 줄이 먼저 실행될 때 중간 잔액이 음수가 되어 실패한다. 같은 거래가 줄을 적은 순서에 따라 성공하기도 실패하기도 한다.
- 한 거래의 줄들은 동시에 일어난 한 사건이다. 순서가 있는 일(충전한 뒤 사용)은 거래를 따로 기록한다.
- 잃는 것: 없다고 본다. 정산은 `[예약 -1000, 사용 +700, 지갑 +300]`처럼 합쳐 적어도 금액이 그대로 보인다.
- 버린 대안: 허용하고 알려진 한계로 둔다. 계획된 흐름에는 부호가 반대인 두 줄이 한 계정에 생기는 경우가 없어서 드문 문제지만, 생기면 원인을 찾기 어렵고 막는 비용이 작다.

### 테스트가 실패하면 이유를 콘솔에 출력한다
- `build.gradle`의 test에 `testLogging`(events 'failed', exceptionFormat 'full')을 넣었다. Gradle 기본 출력은 실패 건수와 HTML 보고서 위치뿐이라, CI 로그에서 이유를 볼 수 없다.

### 빈 멱등 키는 입구에서 막는다 (2026-11-25)
- 키가 null이거나, 비어 있거나, 공백(빈칸, 탭, 줄바꿈)만 있으면 `IllegalArgumentException`을 던진다. 줄 검사보다 먼저, DB에 닿기 전에 확인한다.
- 빈 문자열을 막는 이유: 유일 제약에게 빈 문자열은 하나의 키다. 서로 상관없는 두 충전이 모두 키를 빠뜨리고 들어오면 둘 다 (TOPUP, "")가 되어, 두 번째 충전이 "이미 처리한 요청"으로 취급된다. 기록되지 않은 채 첫 거래의 번호와 함께 성공으로 돌아오므로, 돈이 들어가지 않았는데 아무도 모른다. 이 동작은 코드를 읽고 판단한 것이고 테스트로 재현하지는 않았다.
- null을 막는 이유: `idempotency_key`가 NOT NULL이라 DB가 거절하므로 돈이 틀어지지는 않는다. 다만 DB 오류로 나오면 호출한 쪽이 원인을 알기 어렵다. 입구에서 막으면 메시지로 바로 알 수 있다.
- 공백만 있는 키도 막는 이유: 키를 빠뜨린 것과 구분되지 않는다. `isBlank()`로 확인한다.
- 줄 검사(`checkLines`)에 넣지 않고 `record` 안에 따로 둔다. 줄을 검사하는 메서드에 키 검사가 섞이지 않게 하기 위해서다. 세 줄이라 메서드로 빼지는 않았다.
- 관찰용 테스트는 쓰지 않았다. 결과가 어떻게 나오든 결론(막는다)이 같기 때문이다. 결과에 따라 설계가 달라질 수 있을 때만 먼저 관찰한다.
- 버린 대안: 막지 않고 호출하는 쪽을 믿는다.

### 미정
- 같은 키의 요청이 동시에 올 때: 앞 요청이 커밋하기 전에 뒤 요청의 INSERT가 기다리는지, 앞 요청이 롤백하면 어떻게 되는지, 기존 번호 조회가 0줄이 될 수 있는지. 5일차 동시 요청 테스트에서 확인한다.
- 멱등 키의 길이. 칸이 VARCHAR(100)이라 그보다 긴 키는 DB에서 거절된다. 입구에서 길이를 확인할지는 키를 만드는 규칙을 정할 때 본다.

## 범위 변경 (2026-11-24)

### 화면을 넣는다
- 원래 계획은 화면 없이 API 문서와 Grafana였다.
- 바꾼 이유: 돈이 지갑에서 예약으로, 예약에서 사용으로 움직이는 흐름과 지출 내역을 눈으로 시연하기 위해서다.
- 화면은 별도 저장소(usage-billing-front)에 두고 Claude가 만든다. 백엔드 역량의 증거로 삼지 않는다.
- 프론트와 백엔드는 저장소와 배포를 따로 한다. 이유: 직접 쓴 백엔드 커밋이 프론트 커밋에 섞이지 않고, 빌드 도구(Gradle, npm)가 공유하는 것이 없다.
- 버린 대안: 화면 없이 Grafana만. 모노레포.

### 인증을 넣는다
- 원래 계획에는 인증이 없었다.
- 바꾼 이유: owner_id를 요청이 스스로 말하면 남의 지갑을 쓸 수 있고, 충전 알림 주소를 아는 누구나 잔액을 만들 수 있다. 돈이 움직이는 입구마다 상대를 확인한다.
- 방식: 충전 알림은 서명(HMAC)과 시각 확인, 고객 API는 API 키, 화면은 로그인과 세션. 권한은 소유 확인과 운영자 역할.
- 인증 코드는 직접 쓴다. Spring 인증을 익히는 것이 목적이다.
- 세부(세션과 JWT 중 선택, 키 저장 방식 등)는 만들 때 정한다.

### 늘어난 범위는 일정에 넣지 않는다
- 인증, 꼬리표별 지출 조회, 평가 세트 보관함, LiteLLM 한도 초과 비교 실험.
- 날짜를 정하지 않고 진행 속도에 맞춰 넣는다. plan.md의 기존 일정과 "줄이는 순서"는 그대로 둔다.
- LiteLLM 비교는 현재 버전에서 재현되는지 확인하지 않았다. 재현을 먼저 확인한 뒤 실험으로 넣을지 정한다.

### API에서 정한 것
- 금액은 micros를 JSON 문자열로 주고받는다. JS 숫자는 2^53부터 정수를 정확히 담지 못한다.
- 진행률은 주기 조회(GET /jobs/{id})로 한다. SSE는 넣지 않는다.
- 작업 목록(GET /jobs)을 추가한다. 없으면 화면에서 작업 번호를 알 방법이 없다.

### 실서비스 확장 순서
- 본인 키로 실제 실행 → 팀 예산 관리 → 크레딧 엔진 공개 → 실제 결제.
- 본인 키로 실행: 사용자가 자기 LLM 키를 등록한다. 공급자가 그 사람에게 직접 청구하므로 서비스는 돈을 받지 않는다. 충전은 결제가 아니라 스스로 정하는 한도가 된다. 본 5주차의 실제 모델 시연이 이 자리다.
- 팀 예산 관리: 키 하나를 등록하고 팀원에게 예산을 나눠 준다.
- 앞의 두 단계는 돈을 받지 않으므로 사업자 등록 없이 간다. 크레딧 엔진 공개는 1/23 이후, 실제 결제는 사업자 등록 뒤의 일이다.
- 버린 대안: 처음부터 결제를 받는 서비스로 만들기. 사업자와 법규가 일정에 들어가지 않는다.

### 확장을 위한 자리는 각 기능을 만들 때 넣는다
- 지금 미리 넣지 않는다. 실데이터가 없어서 칸 추가는 Flyway 파일 하나로 언제든 되고, 옮길 데이터가 없다.
- 지갑의 주인을 워크스페이스로 둘지: 사용자 표와 인증을 만들 때 정한다. `owner_id`는 이미 문자열이라 지금 바꿀 것이 없다.
- 충전 거래의 출처 종류(시험, 예산 배정, 결제): 충전 API를 만들 때 정한다. "원인 칸은 지금 넣지 않는다"는 결정을 그때 다시 본다.
- 공급자 호출부 교체와 응답 유실 비용의 부담 주체: 사용자 키로 부르면 공급자가 사용자에게 직접 청구하므로 "플랫폼이 부담한다"가 성립하지 않는다. 손실 분개의 상대 계정(미정)과 함께 본 3주차에 정한다.
- 통화 칸과 적용 시작일이 있는 단가 표: 작업 제출 API를 만들 때 정한다.
- 원장과 작업의 분리: 이미 그렇다. `record`는 거래 종류, 키, 줄만 받는다. 예약·정산을 만들 때 이 경계를 지킨다.
- 지갑 내역의 거래 직후 잔액: 원장에 그 값이 없다. 조회할 때 계산할지, 원장에 칸을 둘지, 화면에서 뺄지는 지갑 내역 조회 API를 만들 때 정한다.
